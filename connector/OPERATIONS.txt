再開に必要な設定
ブラウザの既存ログイン経路、または対象アカウントでWorkers Scripts Edit / Workers KV Storage Editが使えるAPI認証。
ボタンのPages bindingsも設定する場合はCloudflare Pages Editも必要。
アカウント対象を上記IDに指定する。秘密値はInfisicalで管理し、文書・ログ・argvへ出さない。
GitHubサーバー用認証は対象repoのActions read/write。既存GH CLIの広い個人認証を自動転用しない。

公開順序（本人の公開指示を受けてから）
1. 既存mainの更新を取り込み、workflow入力追加とボタンをGitHub経由で反映。
   元の作業ツリーには他者の未commit変更があるため、この分離worktreeを使う。
2. このWorker専用のOAUTH_KV namespaceを作成。既存アプリの認証KVを流用しない。
3. Infisicalにランダム接続コードの原値を保存し、SHA-256だけをWorker bindingに設定。
4. deployment.template.jsonのbindingsを実値で構成し、実際のHTTPS originをPUBLIC_BASE_URLへ設定。
   ALLOW_LOCAL_OAUTHは本番に設定しない。GITHUB_ITO_SYNC_TOKENはserver側のみ。
5. HTTPS上で未認証401、OAuth discovery、PKCE/同意画面/トークン更新、tools/listを確認。
6. 本人の実更新指示で1回だけworkflow_dispatchし、操作固有IDで本番hash照合の成功を確認。
7. docs/ito-connector-handoff.txtに実URLを記入し再読。接続コードは本文に記載しない。
8. 伊藤さんご自身のChatGPTから接続できたことを別途確認。
   ローカル試験合格を、本人アカウントでの接続成功と同一視しない。

ローカル検証
Node 24推奨。connector/でnpm ci、npm run build、npm test。
ルートでnode --test tests/publish.test.mjs tests/publish-client.test.mjs。
npm run previewはlocalhost:18817。ダミー認証とmock GitHubのみを使う。
テストは実際のworkerd、公式OAuthProviderおよびMCP SDKを使用。
本番OAuth KV・GitHubへの送信は行わない。

公開後の失効
接続コードのハッシュを変更しても、発行済みOAuth grantは直ちには失効しない。
既存接続を止める場合はChatGPT側の切断に加え、公式OAuthProviderのgrant失効機能を使う。
作成専用OAUTH_KVの既存キーを不用意に削除しない。
